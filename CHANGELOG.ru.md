## Раунд 74 (прогон на железе, шаг 1: валидатор NUMA_MAP + честный NOTE про промоушен)
* Валидатор HOTSPLIT_NUMA_MAP отвергал ПРАВИЛЬНОЕ значение (блокер прогона):
  regex требовал `node:cpu,cpu;node:cpu` ('0:0,1,2,3;1:4,5,6,7'), тогда как
  реальный потребитель (`patches/numa_bind.py map_from_env`) парсит пары
  `gpu:node` через запятую -- ровно формат из `tp4.env.example`
  ('0:0,1:0,2:1,3:1'). Правильная карта обрывала запуск с «nothing was
  started». Валидатор теперь принимает реальный формат (строго), сообщение
  об ошибке его показывает. Добавлен регрессионный тест.
* NOTE про промоушен врал про `auto`: «engine, namespace and gate will all
  use KV_CACHE_DTYPE=auto» вводит в заблуждение -- `auto` резолвится в
  dtype МОДЕЛИ из config.json ДО старта движка и ДО хеширования namespace
  (для bf16-модели это совпадает с закреплённым bfloat16 -- ТОТ ЖЕ namespace
  кэша). Теперь NOTE объясняет резолв.
## Раунд 73 (согласие на override namespace, равенство HOT_GIB, отрицательный dtype-кейс)
* БЕЗОПАСНОСТЬ (ревью): `KVP_MODEL_NAME` из окружения -- тот же escape
  hatch, что `KV_PERSIST_NAMESPACE` у рецепта, но случайный export молча
  перенаправит кэш в ЧУЖОЙ namespace -- а namespace и есть защита от
  смешения моделей. Теперь override требует ЯВНОГО согласия
  (`KVP_ALLOW_NAMESPACE_OVERRIDE=1`) и печатает громкий WARNING -- и при
  использовании, и когда несогласованное значение ИГНОРИРУЕТСЯ (имя из
  identity имеет приоритет). Тест передаёт флаг согласия -- для этого хук и
  нужен.
* HOTSPLIT_HOT_GIB сравнивается на РАВЕНСТВО на обоих путях (ревью: он был
  в списке разрешённых различий -- дефолт рецепта мог бы разойтись
  незаметно). Parity-тест воспроизводит делегированную схему (один общий
  export) и проверяет, что ОБА docker run несут ОДНО значение (30).
* Тест dtype описывает отрицательную границу (ревью): если `config.json`
  не объявляет dtype (нет `torch_dtype`, нет `dtype`), `auto` НЕ может
  разрешиться -- остаётся `auto` и даёт ДРУГОЙ namespace, чем закреплённый
  `bfloat16`. Это БЕЗОПАСНЫЙ промах кэша, никогда не неверное чтение; пин
  -- no-op только для модели, чей конфиг объявляет свой dtype.
## Раунд 72 (поведенческий тест dtype, полный parity с персистом и allowlist)
* KV_CACHE_DTYPE -- сама ПОДСТАНОВКА (ревью: старый тест проверял только
  комментарий): `tests/test_engine_delegation.py` теперь запускает НАСТОЯЩИЙ
  `resolve_effective_identity` с фейковым `config.json`
  (`torch_dtype: bfloat16`) -- `auto` и закреплённое `bfloat16` дают ОДНО и то
  же значение и ОДИН и тот же namespace кэша (реальный `CacheIdentity`),
  а `fp8` -- свой. Пин не может сдвинуть namespace прогретого кэша --
  проверено поведенчески, а не комментарием.
* Паритет лаунчеров с ВКЛЮЧЁННЫМ персистом (п.5 чек-листа):
  `tests/test_launcher_parity.py::test_full_docker_run_parity_with_persist`
  гоняет ОБА лаунчера с подключённым коннектором и сравнивает ВЕСЬ
  `docker run` по токенам с ЯВНЫМ allowlist (имена контейнеров, пути
  env-file /live, root- против same-UID-кэшей, явные дефолты HOTSPLIT).
  Список различий ревьюера закреплён как данные; любое отклонение вне
  него роняет тест. Обязательные флаги на ОБЕИХ сторонах:
  `--kv-transfer-config`, `--block-size`, `--enable-prompt-tokens-details`.
* Kv-лаунчер учитывает `KVP_MODEL_NAME` из окружения (точный аналог
  `KV_PERSIST_NAMESPACE` у рецепта) -- оба пути работают под ОДНИМ
  закреплённым namespace (parity-hook); явный override остаётся решением
  оператора (задокументированный escape hatch), никогда -- дефолтом.
