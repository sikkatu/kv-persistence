## Раунд 70 (делегирование: KVP_ENGINE=recipe, дефолт ВЫКЛЮЧЕН)

* ОДИН запуск движка, ДВА пути: `start-all.sh` учитывает `KVP_ENGINE`
  (`kv` — kv-лаунчер, ДЕФОЛТ; `recipe` — аппаратно проверенный
  `run-tp4-hotsplit.sh` с KV_PERSIST=1). Дефолт выключен, старый код движка
  не тронут до прогона на железе — ровно как требовал ревью.
* Чек-лист ревьюера (шаг 2), всё подключено и протестировано:
  * без флага ничего не меняется (контрактный снапшот docker run пинит
    поведение; тест дефолтного пути проверяет, что запускается kv-лаунчер);
  * ОДНО имя контейнера: `start-all` пишет эффективное имя в
    `live/engine_container`; `stop-engine.sh` (kvp down / stop-all.sh) и
    `kvp logs/status` читают его — останавливают именно запущенное
    (recipe называет контейнер mimo-pro-tp4-hotsplit, kv-лаунчер —
    mimo-pro-tp4-kvp);
  * ОДИН источник ключа: общий `~/.config/kvp/api_key` экспортируется как
    API_KEY в окружении — никогда в argv — recipe-лаунчер его переиспользует
    и не генерирует второй;
  * KV_CACHE_DTYPE: закреплён bfloat16 (дефолт рецепта — auto). Разница
    ПОКАЗАНА в тестах и не прячется нормализацией; identity-хеш учитывает
    dtype (каждый dtype -> свой namespace; контракт резолва auto->bfloat16
    проверяется в исходнике лаунчера);
  * коды возврата: recipe-лаунчер работает в форграунде — его exit 1
    (проверка активации) доходит до start-all.sh / kvp up без изменений
    (протестировано: отсутствие маркеров -> exit 1).
* `tests/test_engine_delegation.py` (6 тестов) покрывает чек-лист;
  обязательный identity-gate заглушен (то же устройство, что в
  test_kv_persist_behaviour) — настоящая identity — территория
  kv-persistence.

## Раунд 69 (шаг 2, подготовка: проверка активации в лаунчере рецепта, снапшот контракта)

* Лаунчер рецепта (`run-tp4-hotsplit.sh`) теперь выполняет ТУ ЖЕ проверку
  активации hotsplit/NUMA, что и kv-лаунчер движка (раунд 59), до объявления
  успеха: маркер boot-hook (ACTIVE или намеренный INACTIVE с model-патчами),
  `step hook installed`, `live counter:`, `HOOK STATUS numa_bind=ACTIVE` при
  включённом NUMA, без пустых банков и транзакционных ошибок. Отсутствие
  маркера — exit 1. Это закрывает дыру «делегирование потеряет проверку» ДО
  появления `KVP_ENGINE=recipe`. Отключение: `KVP_SKIP_HOTSPLIT_CHECK=1`.
* Снапшот контракта docker run (`tests/fixtures/launcher-docker-run.txt`,
  тест `test_snapshot_contract`): без флага делегирования финальный
  `docker run` обязан оставаться побайтово идентичным записанному контракту.
  Обновление только намеренное: `KVP_UPDATE_SNAPSHOT=1`.
* Негативные тесты активации (`tests/test_activation_negative.py`): отсутствие
  маркера -> exit 1 со списком `[MISSING]`; полный набор маркеров -> exit 0;
  переключатель отключения работает. Код возврата лаунчера — тот, который
  видят start-all.sh / kvp up (запускают его в форграунде).
* Старые тестовые наборы используют документированный opt-out (их docker-
  заглушка не пишет маркеры, они проверяют другое поведение); сама проверка
  покрыта выделенными тестами.

## Раунд 68 (фикс границы lz4, поведенческий тест парсеров)

* Граница lz4 (находка ревьюера): `max_length=cap - len(out)` становился 0 у
  потолка — а 0 означает БЕЗ ОГРАНИЧЕНИЙ в потоковом API lz4, и бомба на
  100 МиБ возвращалась одним безграничным вызовом. Исправлено на
  `cap + 1 - len(out)` (никогда не <= 0 при len(out) <= cap; лишний байт
  срабатывает в проверке переполнения). Честный кадр не затронут. Заглушка
  теста теперь записывает каждый вызов и проверяет max_length > 0 и
  chunk <= cap+1 на путях бомбы, границы и честного кадра.
* Поведенческий тест парсеров (находка ревьюера: подстроки не ловят дрейф):
  `tests/test_parser_behaviour.py` запускает ОБА парсера (kv-persistence
  env.sh и kvp-common.sh рецепта) на ОДНОМ tp4.env и сравнивает окружения
  ключ-к-ключу. Фикстура покрывает все хитрые правила (раскрытие $HOME,
  кавычки, инлайн-комментарии, # внутри значений, export-префикс,
  комментарии с отступом, невалидные идентификаторы). Тест сразу поймал
  общую семантическую дыру: `KEY = value` сохранял ведущий пробел в значении
  — оба парсера теперь срезают ведущие И хвостовые пробелы (все 5 файлов
  обновлены идентично; контракт побайтового совпадения держит их в синхроне).
* На настоящих кодеках по-прежнему не проверено (в CI нет zstandard/lz4):
  точное поведение zstandard при размере заголовка больше max_output_size и
  реальная граничная семантика lz4. `pytest tests/unit/test_decompress_bomb.py -rs`
  на хосте с пакетами должен дать 0 SKIPPED.
