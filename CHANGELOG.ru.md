# Журнал изменений

Все заметные изменения kv-persistence, новые сверху. Здесь хранятся только
последние 3 раунда (запрос пользователя) — полная история правок в
git-логе ветки `main`.

Версии языков: [English](CHANGELOG.md) | **Русский** | [中文](CHANGELOG.zh.md)

## Раунд 78 (override CONTAINER=, контракт API_KEY с каноническим файлом, честный parity, полная цепочка exit-code)
* `CONTAINER=` из окружения ИГНОРИРОВАЛСЯ на рецептном пути (start-all.sh
  затирал его дефолтом). Приоритет теперь: `CONTAINER` > `KVP_ENGINE_CONTAINER`
  > дефолт -- эффективное имя записывается в `live/engine_container` и
  передаётся рецептному лаунчеру.
* Устранён split-brain `API_KEY` в `run-tp4-hotsplit.sh`: env-ключ шёл на запуск,
  а `~/.config/kvp/api_key` хранил СТАРЫЙ ключ (`live/api_key` зеркалил НОВЫЙ) --
  два разных ключа одновременно. Контракт (как на kv-пути): канонический файл --
  источник истины; явный env `API_KEY` ПОБЕЖДАЕТ и СОХРАНЯЕТСЯ туда с громким
  WARNING.
* Полный parity-тест сравнивал токены docker run через `set()` -- повторяющиеся
  флаги/монтирования и кратность были невидимы. Теперь Counter (multiset) +
  поиск дублей одноразовых флагов + цели монтирований как мультимножество
  (ПОРЯДОК флагов честно вне границ: лаунчеры исторически строят команду в
  разном порядке, docker его игнорирует).
* Exit-code теперь проверяется через ПОЛНУЮ цепочку (`kvp up` -> `exec` ->
  `start-all.sh` -> foreground-рецепт) с произвольным ненулевым кодом, а не
  только exit 1 через start-all.sh.
## Раунд 77 (общие pre-flight для обоих путей движка, честные подписи ipc-test)
* Проверка lmcache RPC (`mp_ping`) и тест CUDA IPC-границы (`ipc-test.sh`)
  были встроены ТОЛЬКО в kv-лаунчер — делегированный рецептный путь
  (`KVP_ENGINE=recipe`) грузил 130 шардов ~15 минут и падал на
  `register_kv_cache` (CUDA_ERROR_MAP_FAILED от `cuIpcOpenEventHandle`) без
  единой проверки перед загрузкой. Тот же класс дефекта, что и в раунде 76
  (проверки, живущие в одном лаунчере, исчезают при переключении дефолта).
  Одна общая функция `env.sh::_kvp_pre_flights` теперь работает на ОБОИХ
  путях до загрузки модели; отказ pre-flight не даёт запуститься («ничего не
  было запущено») и называет честное исправление: запустить кэш-сервер в
  контейнере (`KVP_LAUNCH_MODE=docker`) или под UID движка
  (`KVP_SAME_UID=1`). Честная пометка о границах: pre-flight ловит мёртвый
  канал на старте, но не смерть сервера ПОСЕРЕДИНЕ загрузки (лаунчер по-прежнему
  fail-fast'ит по ошибкам сервера).
* Подписи `ipc-test.sh` больше не врут: «same-UID test -- no root»
  печаталось для ЛЮБОГО `PRODUCER_USER`, включая `0:0` (root-производитель).
  Теперь root-производитель подписывается «root producer» и получает свой
  вердикт PASS («ROOT-PRODUCER result»). Регрессионные тесты воспроизводят всё
  (`tests/unit/test_round77_shared_preflights.py`, 8 тестов, красные на старом
  коде).
## Раунд 76 (ложный SIGPIPE в проверке активации, общая валидация конфига, покрытие TP)
* Проверка активации врала на больших логах движка (ревью, воспроизведено на
  железе): `printf '%s' "$log" | grep -q ...` под `set -o pipefail` --
  `grep -q` завершается на первом совпадении и закрывает пайп, `printf`
  получает SIGPIPE (141), пайплайн «неуспешен» и `if` идёт в ветку «не
  найдено», хотя маркер в логе ЕСТЬ. На 17-минутном логе загрузки ВСЕ четыре
  маркера читались [MISSING] при исправном движке -- а те же пайпы охраняли
  проверки ОШИБОК, и настоящая ошибка могла пройти как успех. Все 8 мест
  (по 4 в лаунчерах) теперь на here-string
  (`grep -q -- "..." <<<"$log"`) -- без пайпа, без SIGPIPE. Регрессионные
  тесты на 100 КиБ-логе покрывают оба направления (маркеры есть → VERIFIED;
  ошибки/маркеры в правильной комбинации → правильный вердикт).
* Валидация конфига HotSplit перенесена в ОБЩИЙ модуль
  (`hotsplit_env.sh::_hotsplit_validate_config`): проверки (формат NUMA_MAP,
  DYN_DECAY 0..1, DYN_MARGIN ≥ 1, DYN_MAX_SWAPS 1..1024, целочисленные и
  float-ручки) жили ТОЛЬКО в kv-лаунчере -- после переключения пути движка
  на рецептный они бы исчезли. Оба лаунчера теперь вызывают одну функцию.
* НОВАЯ проверка (ревью): HOTSPLIT_NUMA_MAP должен ПОКРЫВАТЬ каждый ранг
  GPU 0..TP-1. `numa_bind.py` молча возвращает -1 для отсутствующего GPU и
  при этом сообщает `numa_bind=ACTIVE` -- карта "0:0,1:0" на TP4 привязывала
  2 из 4 GPU и выглядела здоровой. Валидатор теперь называет каждый
  недостающий ранг. Поведенческие тесты (TP4/TP2) в
  `tests/test_hotsplit_validation.py` -- условие переключения дефолта на
  рецептный лаунчер.
* Согласие на override namespace (раунд 73) теперь покрыто:
  `tests/test_namespace_override_consent.py` -- без
  `KVP_ALLOW_NAMESPACE_OVERRIDE=1` унаследованный `KVP_MODEL_NAME`
  ИГНОРИРУЕТСЯ с громким WARNING (имя из identity побеждает); с флагом
  override применяется, тоже с WARNING.
