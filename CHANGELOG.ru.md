Все заметные изменения kv-persistence, новые сверху. Заметки о раундах
теперь живут здесь (длинные технические аудиты остаются в

Версии языков: [English](CHANGELOG.md) | **Русский** | [中文](CHANGELOG.zh.md)

## Не выпущено

## Раунд 54 (аппаратная приёмка зафиксирована)

* Приёмка восстановления после перезапуска ПРОЙДЕНА на целевом GPU-хосте
  (4x RTX PRO 6000, MiMo-V2.6-Pro-MOPD, same-UID, 2026-11-07):
  - сценарий A (рестарт vLLM): cached_tokens=2560, ttft 0с против 17.53с
    холодного (memory hit из L1/RAM);
  - сценарий B (рестарт ОБОИХ сервисов, NVMe сохранён): cached_tokens=2560,
    ttft 0с, **L2-событий чтения = 1** (восстановление с диска доказано);
  - гейт идентичности пройден на каждом этапе, **0 жёстких падений**.
* Машинный вердикт — INCONCLUSIVE только из-за незаданного KVP_CACHE_DEVICE
  (независимые счётчики NVMe недоступны) — задайте его в cache.env.local и
  перезапустите для полного машинного PASS.
* README (EN/RU/ZH), матрица совместимости (EN/RU/ZH) и final-report
  (EN/RU/ZH) обновлены: статус ПРИНЯТО с доказательствами; оставшиеся пункты
  NEEDS TESTING — периферийные и помечены честно.

## Раунд 53 (cold baseline ждёт API)

* Cold baseline в `test-recovery.sh` немедленно слал первый HTTP-запрос и
  падал с сырым Python-трейсбеком (Connection refused), если движок ещё
  грузился или был остановлен. Теперь он ждёт через `api_ready` точно как
  сценарии A/B, а отказ соединения печатает короткое понятное сообщение
  вместо трейсбека.
* `api_ready` сообщает, что именно ждёт (никаких тихих 30-минутных
  циклов).

## Раунд 52 (сценарий B: честная диагностика ошибок)

* `test-recovery.sh` сценарий B: `docker stop` больше не глотает вывод
  ошибки (`>/dev/null 2>&1` прятал реальную причину). Сначала проверяется
  состояние контейнера — уже остановленный/удалённый контейнер НЕ является
  ошибкой (цель — чистый перезапуск кэша при остановленном движке). Реальная
  ошибка показывает вывод docker.
* `PA()` теперь принимает тег сценария явно — старый вариант печатал
  `FAIL(A)` даже для ошибок сценария B. Все вызовы обновлены.

## Раунд 51 (standalone-гейт резолвит MODEL_DIR как лаунчер)

* Standalone `scripts/verify-engine-identity.sh` в новом терминале писал
  `model_dir=unset` -> num_kv_heads/head_dim UNAVAILABLE -> INCONCLUSIVE,
  хотя гейт в самом лаунчере проходил: цепочка резолва (live/model_dir >
  пин идентичности > ~/models) жила ТОЛЬКО в лаунчере. Теперь общий хелпер
  `_kvp_resolve_model_dir` в env.sh используется и там, и там --
  standalone-гейт резолвит точно как лаунчер.
* Поправлен баг устаревшего массива в новом хелпере (остатки сканирования
  каталогов конфига смешивались со сканированием моделей).

## Раунд 50 (MODEL_DIR доходит до гейта + дефолт кодека в конфигах)

* Авто-резолвленный MODEL_DIR не ЭКСПОРТИРОВАЛСЯ, поэтому post-launch гейт
  идентичности (подпроцесс) видел `model_dir=unset`, не мог прочитать
  config.json и отказывался проверять num_kv_heads / head_dim
  (INCONCLUSIVE -> переиспользование кэша заблокировано). Лаунчер теперь
  экспортирует его после резолва.
* `L2 codec: none` при zero-config запуске: `lmcache-server.env` всё ещё
  закреплял `LMCACHE_L2_SERDE=none`, перебивая дефолт раунда 48. Все три
  локальных файла теперь согласованы на `zstd`; тесты фиксируют
  расхождение локалей.

## Раунд 49 (PATH автоматически, мониторинг первым, чистка отчёта)

* `export PATH="$HOME/.venvs/lmcache/bin:$PATH"` больше не нужен
  (пользователь): `env.sh` сам находит venv-каталог lmcache (с учётом
  sudo) и подставляет его в PATH для каждого скрипта. Pre-flight версии
  теперь читает lmcache хоста через venv-python (в системном python3 его
  нет).
* Мониторинг НЕ опционален: шаг 6 Quick-Start и quick start'ы README
  теперь сначала запускают `start-observability.sh`, затем
  `start-cache.sh` (подключается сам, раунд 47b). Метки «Optional» убраны.
* `docs/final-report.{md,ru.md,zh.md}` очищены от всех секций правок по
  раундам (пользователь: они в changelog, ранние исправления запоминать не
  нужно) -- отчёт хранит только проверенный статус и техническую запись и
  ссылается на CHANGELOG.

## Раунд 48 (запуск без конфигурации)

* `bash scripts/run-vllm-with-persist.sh` в новом терминале не требует
  export и флагов: IMAGE резолвится из дайджеста рецепта (запоминается в
  `live/image`), MODEL_DIR — из `live/model_dir`/пина идентичности/
  `~/models`, `KVP_SAME_UID=1` ПО УМОЛЧАНИЮ (root-фолбэк:
  `KVP_SAME_UID=0`), кодек по умолчанию — lossless zstd
  (`USE_LOSSLESS_SERDE=0` для байт-точного raw).
* Единая таблица семантики кодека для env.sh / identity.py / _fold_serde
  (исполняемый тест): пусто -> zstd, `raw`/`none` -> явный raw,
  переключатель важнее конфига. Namespace кэша идентичен в bash и Python
  без единого export.
* Остатки 0.5.3 вычищены и из комментариев кода (доки — раунд 47).

## Раунд 47b (авто-детект наблюдаемости)

  `127.0.0.1:4320` и включает метрики — флаг не нужен (запрос

* README + observability README (EN/RU/ZH) обновлены: порядок «стек →
  кэш»; описания дашбордов Grafana освежены.

## Раунд 47 (документация + честность дашбордов)

* Все доки ссылаются на закреплённый **LMCache 0.5.6** (90 устаревших
  упоминаний `0.5.3` исправлено в README/docs EN/RU/ZH); исторические
  ссылки на старые баги апстрима теперь говорят «до 0.5.6» без
  устаревших номеров версий.
* GPU pre-flight свободной памяти выполняется **после** удаления старого
  движка (лаунчер) и **после** остановки обоих сервисов (test-recovery,
  сценарий B) — в раунде 46 проверка стояла слишком рано и отказывала из-за
  законной VRAM движка (78 ГБ на карту на эталонном хосте).
* Grafana: дашборд *LMCache coordinator* аннотирован — ему нужна
  телеметрия координатора многосерверного режима, в нашем односерверном
  репозитории он законно показывает «No data»; дашборд *LMCache*
  объясняет, что данные появляются только с `USE_OBSERVABILITY=1` на
  сервере кэша.
* Создан этот CHANGELOG (EN/RU/ZH) — заметки о раундах теперь здесь.

* Лаунчер записывает эффективный кодек + namespace в

* Deployment-доки (EN/RU/ZH): правило порядка перезапуска.

## Раунды 45h–45j (same-UID режим + bash-ловушки)

* Режим `KVP_SAME_UID=1`: контейнер движка работает под
  `$(id -u):$(id -g)` (динамический UID, без root), кэши под `/tmp`.
* `HOME`/`USER`/`LOGNAME` задаются для любого UID (страховка при
  отсутствии записи в passwd).
* `PRODUCER_USER` должен быть литеральным присваиванием (ловушка bash
  `${var:+NAME=val}`), закреплено исполняемыми тестами.
* Проверка PID кэш-сервера перенесена под `PERSIST=true`.

## Раунды 45–45g (корень CUDA IPC + ipc-test)

* Корневая причина доказана на железе: `register_kv_caches` падает с
  `CUDA_ERROR_MAP_FAILED`, когда кэш-сервер не под root открывает
  GPU-память, созданную root в контейнере. Два решения: оба под root
  (`sudo`) или один UID (`KVP_SAME_UID=1`).
* Новый `scripts/ipc-test.sh` воспроизводит точный падающий шаг (~1 мин,
  без загрузки модели), подключён к pre-flight; поддержка `PRODUCER_USER`
  для same-UID пробы.

## Раунды 42–44 (версия LMCache + API-drift + диагностика)

* Pre-flight версии LMCache: хост и образ должны совпадать (0.5.6).
* Runtime-патчи адаптированы к API 0.5.6 (`dynamic_store`, `@`-суффикт
  соли в именах файлов нативен в апстриме).
* RPC-ping на уровне протокола (`mp_ping.py`), автоматическая диагностика
  кэш-сервера при смерти движка, `PYTHONFAULTHANDLER=1` при старте сервера.

## Раунд 41 и ранее

* Реальная живость = TCP-подключение (не просто живой PID).
* Гейт идентичности разделён на pre-launch проверку конфига и post-launch
  проверку аргументов контейнера.
* Только lossless-кэш (zstd/lz4/none, fp8/turboquant громко отвергаются),
  трёхъязычные доки, понятные сообщения об ошибках.
