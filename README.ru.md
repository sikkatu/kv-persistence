# kv-persistence — универсальный постоянный KV-кэш для vLLM

<p align="center">
  <img src="docs/assets/og-template.jpg" alt="kv-persistence — постоянный KV-кэш для vLLM на общем диске ВМ" width="820">
</p>

Постоянный слой KV-кэша на диске для vLLM: после перезапуска переиспользуемые
KV-блоки промптов восстанавливаются с NVMe, а не пересчитываются. Целевой
эффект — длинные беседы в чат-клиенте (100 тыс.–1 млн токенов) открываются за секунды,
а не за десятки минут — измеряется на целевом оборудовании скриптом
`scripts/benchmark.sh`; результаты публикуются в
[docs/benchmarks.md](docs/benchmarks.md) по завершении приёмочного прогона
(см. [Статус](#статус)).

Спроектировано для повторного использования с **любой моделью на vLLM на любом
GPU-хосте** — модельно-агностичное ядро отделяет политику от интеграции с
моделью. Аппаратно подтверждён только референсный стек: MiMo-V2.6-Pro на
4× NVIDIA RTX PRO 6000 через рецепт `sikkatu/recipes`. Любая другая модель или
хост — **экспериментальная совместимость** до прохождения приёмочных тестов
(`scripts/test-recovery.sh`); ожидается адаптация лаунчера (патчи / загрузчик
модели) для архитектурно отличающихся моделей.

## Что делает

```
клиент чата → vLLM (TP4) → KV-коннектор (LMCacheMPConnector)
       → lmcache-сервер (отдельный процесс) → L2 (nixl_store_dynamic, POSIX) → NVMe
```

* **Персистентность при рестартах** — данные переживают рестарт vLLM И полный
  рестарт сервиса кэша (`persist_enabled=true`; дисковый индекс лениво
  восстанавливается из имён файлов).
* **Ограниченное хранилище** — жёсткий лимит (1.5 ТБ по умолчанию, настраивается под
  объём NVMe), мягкий порог (90 %) с автоматической LRU-эвикцией; кэш никогда сам себя
  не стирает при старте.
* **Пространства совместимости** — ревизия модели, токенизатор, KV-тип, геометрия
  блоков и чат-шаблон входят в ключ кэша: несовместимые конфигурации никогда не
  читают чужие KV-данные; неопределённость даёт промах, а не неверное попадание.
* **Модельно-агностичное ядро** — политика кэша отделена от интеграции с моделью;
  новая модель добавляет конфигурацию, а не код. KV-данные разных моделей не
  делятся никогда.

## Быстрый старт

```bash
git clone https://github.com/sikkatu/kv-persistence ~/kv-persistence
cd ~/kv-persistence
bash scripts/setup-identity.sh "$HOME/models/<your-model-dir>"   # заполнение И проверка пинов идентичности
bash scripts/preflight.sh               # проверка хоста, хранилища и идентичности
bash scripts/start-all.sh              # ОДНА команда: мониторинг + кэш + движок
#   KVP_ENGINE=recipe  делегирует шаг движка аппаратно проверенному
#   лаунчеру рецепта (sikkatu/recipes, KV_PERSIST=1) -- тот же стек одной
#   командой. ДЕФОЛТ: KVP_ENGINE=kv (собственный лаунчер репо).
#   (или пошагово: start-observability.sh -> start-cache.sh -> run-vllm-with-persist.sh)
bash scripts/stop-all.sh                # остановить всё (данные сохраняются)

API-ключ: ОДИН общий файл для обоих репо (`$HOME/.config/kvp/api_key`,
автогенерация при первом запуске, chmod 600). Переопределение:
`KVP_API_KEY_FILE=`. Легаси `live/api_key` мигрируются автоматически.
bash scripts/test-recovery.sh           # приёмка: рестарт → доказательство переиспользования (exit 0 = PASS)
```
С раунда 48 запуск НЕ требует export и флагов: IMAGE резолвится из рецепта
(запоминается в `live/image`), MODEL_DIR — из `live/model_dir`/пина
идентичности/`~/models`, same-UID по умолчанию, кодек по умолчанию —
lossless zstd (отключение: `USE_LOSSLESS_SERDE=0`).

Каждая команда громко отказывается вместо полурабочей установки: значения
идентичности записывает и проверяет `setup-identity.sh`, `preflight.sh`
контролирует физическое NVMe-устройство, а `test-recovery.sh` завершается
машинным вердиктом.

Постоянный переключатель в production-рецепте — `KV_PERSIST=1` в `tp4.env`
(см. вики «Интеграция с рецептами»); откат — удаление этой одной строки.

**Делегирование движка (`KVP_ENGINE`).** `start-all.sh` умеет выполнять шаг
движка любым из двух путей:

* `KVP_ENGINE=kv` (ДЕФОЛТ) -- `run-vllm-with-persist.sh` этого репо;
* `KVP_ENGINE=recipe` -- аппаратно проверенный `run-tp4-hotsplit.sh` из
  `sikkatu/recipes` с `KV_PERSIST=1`, одной командой, без ручных шагов.

Оба пути делят один ключ (`~/.config/kvp/api_key`, автогенерация на loopback
на ОБЕИХ путях), один дефолт бюджета горячих экспертов и одну запись имени
контейнера (`live/engine_container` пишется при каждом запуске -- поэтому
`stop-engine.sh` / `kvp down` останавливают именно запущенное).
Делегирование пинит `KV_CACHE_DTYPE=bfloat16` (дефолт рецепта `auto`
резолвится в dtype модели -- ТОТ ЖЕ namespace кэша, проверено
поведенчески). Дефолт НЕ переключается, пока прогон на железе не
подтвердит рецептный путь.

Namespace кэша обычно выводится из конфига идентичности (защита от смешения
моделей). Override `KVP_MODEL_NAME` нужен только для parity-тестов и
требует ЯВНОГО согласия: `KVP_ALLOW_NAMESPACE_OVERRIDE=1
KVP_MODEL_NAME=<ns>` -- и печатает WARNING и при использовании, и когда
несогласованное значение игнорируется. Случайный export одного
`KVP_MODEL_NAME` ничего НЕ меняет.

Для VM, где /sys показывает `numa_node=-1`, NUMA-привязке нужна явная карта
GPU→node: `HOTSPLIT_NUMA_MAP="0:0,1:0,2:1,3:1"` -- пары `gpu:node` через
запятую (формат, который парсит `patches/numa_bind.py` и документирует
`tp4.env.example`). Сначала проверьте топологию: `numactl --hardware`.

## Lossless-хранение

Уровень L2 — **только lossless**. KV-блоки на NVMe всегда декодируются обратно
в точные байты, которые произвёл движок: в проекте нет квантизации
fp8 / turboquant / lbq, и любой такой кодек громко отвергается при старте.
Доступны два режима хранения:

* **Lossless-zstd (ДЕФОЛТ)** — `LMCACHE_L2_SERDE=zstd`, используется, когда
  ничего не задано. Чанки сжимаются lossless-кодеком `kvp-zstd`, который
  регистрирует `implementation/kvpersist/compress_serde.py`. Блок, который
  не сжался, хранится сырым, поэтому чанк никогда не растёт более чем на
  одну страницу 4 КиБ. Ожидаемое уменьшение на реальных KV-данных скромное —
  часто цитируемый диапазон примерно **1.1–1.4x**, но это *оценка*, а не
  измерение из этого репозитория: бенчмарк коэффициента сжатия здесь ещё не
  запускался (см. `docs/final-report.md`).
* **Lossless-lz4 (альтернатива)** — `LMCACHE_L2_SERDE=lz4`. Быстрее, ниже
  коэффициент сжатия.
* **Байт-точный сырой (ЯВНЫЙ opt-out)** — `LMCACHE_L2_SERDE=none`. Чанки
  хранятся дословно, идентично несжатому upstream-пути; cache hit возвращает
  точные KV-байты движка. Это ЕДИНСТВЕННЫЙ способ отключить сжатие — оно
  никогда не выбирается неявно.

Каждый фрейм несёт **CRC32 несжатой полезной нагрузки** (формат `KVCZ` v2):
усечённое DMA-чтение, битовый сбой или фрейм, записанный под другим кодеком,
обнаруживаются при десериализации и трактуются как промах кэша — никогда не
возвращаются как молча испорченный KV.

**Зависимости:** сырому opt-out (`none`) пакеты сжатия **не нужны** вообще.
`zstd` требует только `zstandard`, `lz4` — только `lz4`: стартовая проверка
(`require_codec`) проверяет ровно выбранный кодек до старта сервера и никогда
не требует неиспользуемый.

Включить lossless-сжатие на один запуск:

```bash
USE_LOSSLESS_SERDE=1 bash scripts/start-cache.sh     # zstd
USE_LOSSLESS_SERDE=lz4 bash scripts/start-cache.sh   # lz4
```

или постоянно в `configs/generic/lmcache-server.env(.local)`:

```bash
LMCACHE_L2_SERDE=zstd
```

Кодек входит в namespace идентичности кэша: переключение между `none`, `zstd`
и `lz4` превращает ранее сохранённые чанки в безопасный cache **miss** (никогда
не в неверное чтение), и каждый лаунчер (`start-cache.sh`,
`run-vllm-with-persist.sh`, `verify-engine-identity.sh`) резолвит переключатель
в одно и то же эффективное значение.

## Мониторинг (Prometheus + Grafana)

Полный стек наблюдаемости из официального примера LMCache лежит в
`observability/` (OTel Collector + Tempo + Prometheus + Grafana) с
**уже установленными официальными дашбордами LMCache**. Одна команда поднимает
всё:

```bash
bash scripts/start-observability.sh
# или, что эквивалентно:
cd observability && docker compose up -d
```

* **Grafana** → <http://localhost:3000> (анонимный Admin-доступ, без входа).
  Дашборды *LMCache* и *LMCache Coordinator* импортируются автоматически.

**Заметка о честности дашбордов (раунд 18):** дашборды — *официальные* ассеты
LMCache, но они созданы под более новой версией LMCache, чем закреплённая здесь
**0.5.6** (аудит дашбордов ниже проводился по исходникам 0.5.6).
Статическое сравнение с исходниками 0.5.6
(`lmcache/v1/mp_observability/`) показывает: большинство панелей отображают
реальные метрики 0.5.6 (гаuges использования L1/L2, конвейеры store/prefetch,
цикл эвикции, event-bus, гистограммы пропускной способности), но **4 панели из
28** ссылались на метрики, которых 0.5.6 не выдаёт (счётчики prompt/request-hit
токенов lookup, счётчики inflight store/retrieve L0↔L1, счётчики transfer-phase
DMA). Эти панели теперь **переадресованы на реальные метрики 0.5.6**
(`lookup_requested`/`lookup_hit` для hit rate, счётчики чанков `l1_read`/
`l1_write` для активности L0↔L1, `l0_l1_store_throughput` для DMA). Переадресация
— семантическое соответствие по лучшему варианту, а не гарантия апстрима:
метки/единицы могут слегка отличаться от исходного замысла.
Дашборд *LMCache Coordinator* ожидает телеметрию координатора, которую
`mp_coordinator` до 0.5.6 не экспортирует (48 рядов без аналога в 0.5.6);
этот репозиторий координатор не запускает, поэтому дашборд обоснованно остаётся
пустым.
* **Prometheus** → <http://localhost:9091>
* **Tempo** → <http://localhost:3200> (трейсы)
* **OTLP gRPC** → `localhost:4320` — сюда кэш-сервер отправляет метрики.

**Безопасность:** каждый публикуемый порт привязан только к `127.0.0.1`
(loopback-контракт из `docs/security.md`). Grafana работает с анонимным
Admin-доступом и отключённой формой входа — выставление на `0.0.0.0`
раздало бы админку на всю сеть. Для доступа с другого хоста поставьте
пред стек аутентифицирующий обратный прокси. Все образы закреплены на точные
версии (без `:latest`) — как и всё остальное в проекте.

**Docker-режим:** когда кэш-сервер работает в sidecar-контейнере
(`KVP_LAUNCH_MODE=docker`), `start-cache.sh` автоматически переписывает
`localhost`/`127.0.0.1` в OTLP-endpoint на `host.docker.internal` — внутри
контейнера `localhost` это сам контейнер, и метрики иначе никогда не дошли
бы до коллектора.

Телеметрия включается АВТОМАТИЧЕСКИ с раунда 47b: `start-cache.sh`
обнаруживает коллектор на `127.0.0.1:4320` и начинает отправку -- сначала
поднимите стек, затем (пере)запустите кэш:

```bash
bash scripts/start-observability.sh   # коллектор + Prometheus + Grafana
bash scripts/start-cache.sh           # метрики идут сами
```

Явное переопределение: `USE_OBSERVABILITY=1` принудительно включает,
`KVP_NO_OBSERVABILITY=1` принудительно выключает,
`KVP_OTLP_ENDPOINT=http://host:port` задаёт свой endpoint.

Панели, за которыми стоит следить на дашборде LMCache:

| Панель | Что показывает |
|---|---|
| cache hit rate | соотношение hit / miss на запрос — главный сигнал здоровья |
| L1 / L2 usage | заполнение уровней относительно ёмкости (L1 = RAM хоста, L2 = NVMe) |
| store / retrieve throughput | байты в секунду, записываемые на NVMe и читаемые с него |
| evictions | LRU-эвикции по уровням — растущий темп означает слишком малый бюджет |
| restore (prefetch) time | как быстро перезапущенный сервер наполняет L1 из NVMe |

Остановить стек: `bash scripts/start-observability.sh --down` (тома данных
сохраняются).

## Расчёты под KV ~200 ГБ

Разговору с KV до ~200 ГБ нужно место под них плюс запас на рост:

| Параметр | Рекомендация |
|---|---|
| `KVP_L1_SIZE_GB` (буфер RAM хоста) | 30–40 ГБ |
| `KVP_CACHE_BUDGET_GB` (жёсткий лимит L2) | ≥ 250–300 ГБ на **выделенном локальном NVMe** |
| `KVP_CACHE_ROOT` | путь на этом NVMe, никогда не сетевой шар |
| `KVP_CACHE_DEVICE` | закрепить блочное устройство, чтобы `preflight.sh` доказал: кэш на нужном диске |

Поставляемый дефолтный бюджет — 1500 ГБ, потому что эталонный хост делит один
том между ОС, моделью и кэшем; на выделенном NVMe снизьте его до 300 ГБ.
`KVP_CACHE_BUDGET_GB`, `KVP_CACHE_ROOT` и `KVP_CACHE_DEVICE` живут в
`configs/generic/cache.env(.local)`.

## Быстрый старт: lossless + Grafana

```bash
# 1. Мониторинг (стартует ПЕРВЫМ -- кэш сам подключается к нему)
bash scripts/start-observability.sh

# 2. LMCache + vLLM (lossless zstd -- ПО УМОЛЧАНИЮ с раунда 48)
bash scripts/start-cache.sh
bash scripts/run-vllm-with-persist.sh
```

`USE_LOSSLESS_SERDE` должен быть одинаков для обеих команд — он входит в
namespace идентичности кэша. С раунда 46 лаунчер также пишет эффективный
кодек в `$KVP_CACHE_ROOT/engine-identity.env`, и отдельные скрипты читают его
автоматически (переключатель > пин `KVP_L2_SERDE` > файл) — новый терминал
больше не показывает ложное несовпадение `identity=none != engine/config=zstd`.
Пин `KVP_L2_SERDE` в `identity.env.local` можно закрепить и явно. Не задавайте
ничего, чтобы получить дефолтный lossless-zstd; явный `LMCACHE_L2_SERDE=none` — для байт-точного сырого режима.

## Статус

Реализация завершена; офлайн-тесты зелёные. **Приёмка восстановления после
перезапуска ПРОЙДЕНА на целевом GPU-хосте (4x RTX PRO 6000, 2026-11-07)**: после
полного перезапуска ОБОИХ сервисов первый запрос обслужен из кэша
(`cached_tokens=2560`, ttft 0с против 17.53с холодного) с доказательством чтения
с L2/диска (L2-событий чтения = 1). Оставшиеся непроверенные возможности помечены
`NEEDS TESTING` / `BLOCKED` в [docs/final-report.md](docs/final-report.md) —
непроверенное не выдаётся за работающее.

## Правила проектирования

* Production-рецепт (`sikkatu/recipes`) для проекта **только для чтения**.
* Эндпоинты управления (lmcache HTTP + ZMQ) ограничены loopback, корень кэша
  `0700`. Loopback — это НЕ аутентификация: другой локальный пользователь того
  же хоста может обратиться к этим портам. При совместном использовании хоста
  нужна дополнительная изоляция (см. docs/security.md).
* В дереве нет учётных данных, токенов, текстов промптов и данных кэша.
* Все задокументированные команды работают как есть после экспорта
  переменных-предусловий (`IMAGE`, `MODEL_DIR`, `API_KEY`) — «Быстрый старт»
  даёт линейный порядок.

## Как подключить свою модель

Слой кэша модельно-агностичен — добавление модели НЕ требует правок кода:

1. Скопируйте референсный пример и переименуйте в id вашей модели:
   ```bash
   cp -r "$REPO/configs/mimo-v2.6-pro" "$REPO/configs/<ваша-модель>"
   ```
2. **Выберите конфиг модели** — при наличии второй конфиг-папки скрипты больше
   не выбирают её автоматически (неоднозначная раскладка отклоняется, а не
   угадывается):
   ```bash
   export KVP_MODEL_CONFIG=<ваша-модель>
   ```
   `KVP_MODEL_CONFIG` читают `setup-identity.sh`, `start-cache.sh`,
   `run-vllm-with-persist.sh`, `verify-engine-identity.sh` и загрузчик конфигов
   `kvpersist`. `CONFIG_FILE` (только у `setup-identity.sh`) дополнительно
   позволяет указать конкретный файл для записи; обычно он не нужен.
3. Отредактируйте `configs/<ваша-модель>/identity.env`:
   * `KVP_MODEL_ID` = HF-id вашей модели (или любое уникальное имя).
   * `KVP_TP_SIZE`, `KVP_BLOCK_SIZE`, `KVP_NUM_KV_HEADS`, `KVP_HEAD_DIM`,
     `KVP_MAX_MODEL_LEN`, `KVP_KV_CACHE_DTYPE` = KV-геометрия, которую
     vLLM отчитывает для ВАШЕЙ модели (см. `docs/architecture.md`,
     «identity fields»).
   * `KVP_CONNECTOR_VERSION` = дескриптивный тег вашей связки vLLM+LMCache.
4. Запустите `bash scripts/setup-identity.sh "$HOME/models/<ваша-модель>"` —
   ревизии/digest заполнятся автоматически.
5. Запускайте с экспортированным `KVP_MODEL_CONFIG=<ваша-модель>`; скрипты
   разрешают `configs/<ваша-модель>/` по нему (см. `docs/deployment.md`).
Каждая модель получает собственное пространство имён кэша — KV-данные разных
моделей никогда не смешиваются, а изменение любого поля идентичности безопасно
переводит в промах кэша. Для изоляции по пользователям/арендаторам используйте
`cache_salt` (исправлено на уровне дискового ключа в раунде 15 патчем
`kvpersist/salt_filename_patch.py`, который применяют все лаунчеры) или
`lmcache_model_name(extra_discriminator=...)` / отдельный корень кэша.
**Примечание:** поддержка моделей кроме MiMo не тестировалась до прогона на
железе; рассматривайте `configs/mimo-v2.6-pro/` как единственный референсный
референс и ожидайте адаптации лаунчера (патчи/загрузчик модели) для
архитектурно отличающихся моделей.
