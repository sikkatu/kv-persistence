## Архитектура и выбранный бэкенд

```
Клиент чата → vLLM (TP4, prod-рецепт не изменён) → LMCacheMPConnector
            → лаунчер kv-persistence (пакет kvpersist + скрипты) → NVMe
```

Уровень хранения — LMCache `nixl_store_dynamic` + POSIX (persist_enabled=true,
детерминированный файл на ключ чанка, ленивое восстановление индекса после
рестарта ОБОИХ процессов; max_capacity_gb = 1500 ГБ по умолчанию, LRU-эвикция
с мягким порогом 0.9).

## Изоляция по идентичности на уровне хранилища LMCache (review P1-3)

Namespace идентичности теперь принудительно разделяет данные в РЕАЛЬНОМ
хранилище LMCache, а не только в локальных метках. Проверено по исходникам
закреплённого LMCache 0.5.3 и живым прогоном запись/поиск (интеграционный тест
`test_identity_namespace_isolates_lmcache_storage`, см. docs/benchmarks.ru.md):

* Ключ кэша LMCache (`ObjectKey.model_name`) входит и в ключ, и в имя файла L2
  адаптера `nixl_store_dynamic`
  (`<safe_model_name>_<kv_rank>_<group>_<chunkhash>.bin`).
* `CacheIdentity.lmcache_model_name()` встраивает namespace в этот
  `model_name`, поэтому изменение ЛЮБОГО поля идентичности переносит данные на
  другой ключ И в другой файл на диске. Доказано по каждому полю: поиск
  изменённой идентичности возвращает `0/N` чанков на уровне API LMCache там,
  где исходная возвращает `N/N`.
* **Остаточный пробел — ЗАКРЫТ на уровне дискового ключа (раунд 15)**:
  `cache_salt` входит в равенство ключа, но апстрим `nixl_store_dynamic` НЕ
  включает его в имя файла (адаптеры fs/s3/bigtable учитывают). Измеренная
  утечка (`store salt=tenantA`, `lookup salt=tenantB` -> `4/4` чанка после
  рестарта) закрыта патчем `kvpersist/salt_filename_patch.py`, который
  добавляет соль в имя файла L2 и применяется ВСЕМИ лаунчерами. Проверено
  живьём: `store salt=tenantA`, `lookup salt=tenantB` -> `0/4` чанка
  (`test_cache_salt_isolates_l2_storage` громко падает, если утечка вернётся).
  Запуск голого `lmcache server` БЕЗ патча сохраняет апстрим-поведение: тогда
  используйте `lmcache_model_name(extra_discriminator=...)` или отдельный
  корень кэша на тенанта.

## Идентичность весов — P0-исправление

Новая реализация `scripts/setup-identity.sh` хеширует СОДЕРЖИМОЕ каждого шарда
(SHA-256), а не только имя+размер. Прогнан смоук: байтовая подмена шарда при
неизменных имени и размере теперь меняет отпечаток (`pytest
tests/unit/test_fingerprint_content.py` — 3 регрессионных зелёных). Кэш хешей
шардов ускоряет повторные запуски. Режим `fast` (только имя+размер) доступен
через `KVP_FINGERPRINT_MODE=fast` с явным предупреждением о риске — не для проды.

## Проверка идентичности движка — обязательный барьер

`scripts/verify-engine-identity.sh` (вызывается перед использованием кэша в
`test-recovery.sh`) — сверяет пины identity.env с реальными аргументами
движка (через `docker inspect`) и геометрией модели из config.json.
Три исхода: VERIFIED(0) / MISMATCH(4) / INCONCLUSIVE(5).
**INCONCLUSIVE = отказ от переиспользования кэша**, а не «ошибок нет, значит ок».

## Тест восстановления — протокол v2 (по замечаниям ревью)

* Маркеры позиции лога до каждого запроса — только свежие события считаются.
* Store-before-restart: блоки должны быть реально записаны в L2 до рестарта.
* Различие L2 (диск) от L1 (RAM) в доказательствах чтения.
* cached_tokens == `null` обрабатывается: MISSING → INCONCLUSIVE, а не «отсутствие
  попадания» по умолчанию.
* Физические счётчики чтения с NVMe (`/sys/block/<dev>/stat`) как независимое
  подтверждение логов (при заданном `KVP_CACHE_DEVICE`; без него — INCONCLUSIVE).
* Три-состоятельный вердикт: PASS(exit 0) / INCONCLUSIVE(exit 5) / FAIL(exit 1).

## Lossless-кодек L2 и стек наблюдаемости (задача)

В текущем задании требовались два дополнения; оба реализованы БЕЗ форка LMCache
и без изменений production-рецепта.

### 1. Только lossless-хранение L2

Upstream LMCache 0.5.3 регистрирует лишь lossy- (fp8, turboquant) и шифрующие
(aesgcm) serde — lossless-сжатия upstream нет. Этот репозиторий добавляет его
через `implementation/kvpersist/compress_serde.py`, который регистрирует
типы serde `kvp-zstd` / `kvp-lz4` / `kvp-raw` в собственном реестре LMCache в
runtime (тот же паттерн лаунчера, что и salt-filename патч; теперь они
объединены в `implementation/kvpersist/launch.py`).

* Дефолт `LMCACHE_L2_SERDE=none` — байт-точные сырые чанки, идентичные
  несжатому upstream-пути. Ничего не трансформируется.
* `LMCACHE_L2_SERDE=zstd|lz4` (или операторский переключатель
  `USE_LOSSLESS_SERDE`) — lossless-сжатие. Несжимаемый блок хранится сырым,
  поэтому чанк никогда не растёт более чем на одну страницу 4 КиБ
  (28-байтный заголовок фрейма + паддинг до страницы). Часто цитируемое
  уменьшение 1.1–1.4x — ПЛАНОВАЯ ОЦЕНКА из экосистемы LMCache, а не измерение
  из этого репозитория: бенчмарк коэффициента сжатия здесь ещё не запускался.
* Lossy-кодеки (fp8 / turboquant / lbq / cachegen / kivi) громко ОТКАЗЫВАЮТСЯ
  при старте — lossless это контракт, а не дефолт, который может измениться.
* Кодек сворачивается в namespace идентичности кэша (`l2_serde`) и в shell
  (`scripts/env.sh _kvp_resolve_l2_serde`), и в Python-загрузчике
  (`kvpersist.identity`); unit-тесты утверждают, что оба согласованы
  (`tests/unit/test_lossless_serde_switch.py`). Смена кодека — безопасный
  cache miss, никогда не неверное чтение.
* Формат фрейма `KVCZ` v2 несёт CRC32 несжатой полезной нагрузки: усечённое
  DMA-чтение, битовый сбой или фрейм другого кодека обнаруживаются при
  десериализации и трактуются как промах кэша.
* Паддинг после полезной нагрузки явно зануляется — переиспользованный блок
  L1-слаба не должен подмешивать байты чужого тенанта в наш кэш-файл
  (`tests/unit/test_compress_serde.py::test_padding_is_zeroed`).
* Fail-fast: перед стартом сервера `require_codec()` проверяет биндинги
  **выбранного** кодека (probe в host-venv или probe ВНУТРИ контейнера в
  docker-режиме). Кэшу с `LMCACHE_L2_SERDE=none` пакеты сжатия не нужны вообще
  — lz4 и zstandard требуются только при фактически выбранном их кодеке.
  Отсутствующие биндинги обрывают запуск вместо достижения READY и падения
  внутри serde-потока.
* Патч размера L2-файла ставится ТОЛЬКО когда реально создаётся kvp-* serde;
  при `LMCACHE_L2_SERDE=none` класс адаптера не трогается (байт-в-байт
  upstream load/store), поэтому короткое DMA-чтение не может быть замаскировано
  нашей обёрткой на raw-пути.

**Честный статус:** логика фрейма serde покрыта unit-тестами (round-trip,
фрейминг, отвержение повреждённых фреймов, passthrough несжимаемых данных)
БЕЗ установленных torch/lz4/zstandard. Сквозной путь через
`SerdeL2AdapterWrapper` LMCache и DMA-запись `nixl_store_dynamic` — **НУЖДАЕТСЯ
В ТЕСТИРОВАНИИ на целевом GPU-хосте**, как и остальная аппаратная приёмка.
Два точечных runtime-патча (`_install_size_patch`) заставляют размер файла на
диске следовать за сериализованным фреймом, а не за полной L1-аллокацией; они
покрыты логикой юнит-уровня, но ещё не проверены на железе.

## Правки по итогам ревью, раунд 18

**Критичные (ложный FAIL / ложная безопасность):**
* **Сценарий A падал бы на исправной системе**: `test-recovery.sh` жёстко завершался
  с FAIL, если сценарий A (рестарт только vLLM) не давал L2-событий чтения. Но сервис
  кэша и его L1 (RAM хоста) переживают этот рестарт, поэтому исправная система
  отдаёт запрос из L1 и пишет `(N L1, 0 L2)` — это задокументированное «memory hit».
  Теперь A принимает memory hit (PASS при одном `cached_tokens>0`), дисковый сигнал
  только информативный, а L2-чтения обязан требовать только сценарий B (полный
  рестарт, пустая L1). Проверка финального вердикта «reuse без L2-доказательств»
  тоже перенесена с A+B на B. Регэксп с `(N L1, N L2)` (оба счётчика ненулевые)
  сохранён как вспомогательный сигнал для B, но не единственный шлюз.
* **tmp_guard был бесполезен в docker-режиме (P1)**: `start-cache.sh` в docker-режиме
  поднимает сервис в контейнере БЕЗ `--pid=host`, поэтому PID маркера живёт в
  неймспейсе контейнера — CLI на хосте сверял его с ХОСТОВЫМ `/proc`, не находил
  процесс и считал ЖИВУЮ запись мёртвой; оставалось только 15-минутное окно по
  mtime. Исправлено на уровне механизма: `register_write` записывает в маркер
  ID PID-неймспейса писателя (`/proc/self/ns/pid`), а `writer_alive` при
  принадлежности маркера чужому неймспейсу переключается на HEARTBEAT маркера
  (свежий mtime ≤ `HEARTBEAT_ALIVE_SEC` = живой, старше — остаток краша).
  Маркеры того же неймспейса проверяются как раньше — точно по
  /proc(pid, start-time). Старые двухстрочные маркеры (пустой ns) ведут себя как
  прежде. Тесты: `test_writer_alive_falls_back_to_heartbeat_in_foreign_pid_ns`,
  `test_marker_records_writer_pid_namespace`.

**Серьёзные (дашборды вралы / гонки в сценариях):**
* **Grafana «Cache Hit Rate» (и ещё 3 панели) были пусты на 0.5.3**: дашборды
  скопированы из более новой LMCache, чем закреплённая 0.5.3. Проверено по исходникам
  0.5.3 (каждый `create_counter`/`register_gauge` в `lmcache/v1/mp_observability/`):
  4 панели из 28 ссылались на метрики, которых 0.5.3 не выдаёт —
  `lookup_prompt_tokens_total` / `lookup_request_hit_tokens_total` (Cache Hit Rate,
  Lookup & Engine), `num_submitted/finished_stores|retrieves` (Inflight GPU Copies)
  и `transfer_phase_*` (MP Transfer DMA). Эти панели переадресованы на РЕАЛЬНЫЕ
  метрики 0.5.3 (lookup_requested/hit, l1_read/l1_write, l0_l1_store_throughput).
  ВАЖНАЯ корректировка по ходу правки: `l1_memory_usage_bytes`, `l2_usage_bytes`,
  `num_inflight_l2_*`, `active_prefetch_jobs` и gauge'ы `event_bus_*` в 0.5.3
  ЕСТЬ (регистрируются через `register_gauge` в
  `l1_manager.py`/`storage_manager.py`/`lookup.py`) — первый патч ошибочно заменил
  и их; эта перезамена откачена. README теперь прямо говорит, что «официальные»
  дашборды сделаны под более новую LMCache, перечисляет именно эти 4 переадресованные
  панели и поясняет, что дашборд **Coordinator** обоснованно остаётся пустым (этот
  репозиторий координатор не запускает; 48 его рядов не имеют аналога в 0.5.3).
* **L2_bytes считал маркеры реестра**: маркеры `.kvp-active-writes/` — служебные,
  не кэш-данные; их учёт мог дать ложное «L2 shrank». Теперь исключены из
  `L2_bytes`/`find`.
* **Асинхронная запись L2 обгоняла замер байт**: между `ask cold` и `L2_bytes` не было
  паузы, но записи завершаются асинхронно — возможно ложное «ничего не сохранено».
  `wait_l2_quiet()` теперь опрашивает `L2_bytes` до стабилизации перед сравнениями
  B0/B_WARM и B_BEFORE/B_AFTER.

**Мелкие:**
* **preflight только предупреждал о `bf16`/`fp16`**: неверное написание CacheDType
  останавливает движок, поэтому preflight теперь `die`, а не предупреждает и не

* **Опечатка «BLOAT16»** в шапке лаунчера исправлена (BFLOAT16).
* **heredoc в `ask()` стал неквотированным** (`<<PYEOF`): любой `$` или обратная

* **Дефолт `LMCACHE_LOG_LEVEL` vs совет**: конфиг дефолтился DEBUG, а комментарий

  пробрасывается в docker-контейнер (`-e LMCACHE_LOG_LEVEL=…`) — все три режима

* **Проверка утечки токенов в DEBUG-логах (по запросу ревью)**: выполнена статическая
  проверка каждого `logger.debug` закреплённой 0.5.3 — DEBUG-логи несут только
  счётчики, размеры, session/request id и хэши ключей чанков, никогда не токены и
  не текст промпта. Единственный путь сырых ключей — опциональный файловый логгер
  `--lookup-hash-log-dir` (ВЫКЛ., если оператор не задал). Задокументировано в

**P3 — «два пути, один кэш» было ложью по умолчанию**: рецепт передавал
`KVP_SERVED_MODEL_NAME=mimo-pro`, а лаунчер kv-persistence использовал
`basename(MODEL_DIR)` (напр. `MiMo-V2.6-Pro-MOPD`) — одинаковый хэш, разные
префиксы, кэш никогда не шарился (ревьюер замерил `mimo-pro/d2089a2f…` vs
`MiMo-V2.6-Pro-MOPD/d2089a2f…`). Дефолт специализированного лаунчера теперь
следует `SERVED_MODEL_NAME` (строке вызова движка), оба пути дают один
`model_name`. Покрыто `tests/unit/test_launcher_namespace_coherence.py`
(исполняет реальную строку дефолта) и `test_served_model_name_prefix_is_stable`.

**P4 — гейт подставлял `block_size=16` как факт**: `DEFAULT_BLOCK_SIZE` равен 16
в закреплённой сборке, но `platforms/interface.py` может выбрать другое значение
через `get_preferred_block_size`, и движок пишет «Setting kv cache block size
to N». Гейт больше не подставляет 16: читает `config.json`
(`block_size`/`hybrid_block_size`), затем строку лога движка, а при отсутствии
обоих — INCONCLUSIVE (наблюдаемый факт нельзя выдавать за факт). Ветка
`KV_PERSIST=1` по-прежнему фиксирует `--block-size` (теперь через
пространственную ручку `KV_PERSIST_BLOCK_SIZE`, закрывая коллизию `BLOCK_SIZE`).

**P5 — дефолты рецепта сменились для всех запусков** (утверждение «byte-identically
to before» было ложным): `MAX_NUM_SEQS` 1→2 и `KV_CACHE_DTYPE` возвращён в
`auto` (ПРОВЕРЕННЫЕ бенчмарки шли на auto). По решению оператора `MAX_NUM_SEQS=2`
ОСТАЁТСЯ дефолтом (без параллельного запроса скорость не падает, удобнее), так
что старое утверждение заменено явным ПРИМЕЧАНИЕМ в README ×3 /
tp4.env.example ×3: два дефолта изменены для всех запусков и как точно
воспроизвести условия старых замеров.

**Тесты теперь ВЫПОЛНЯЮТ блок** (замечание ревьюера, что текстовые тесты ничего
из этого не ловили): `tests/test_kv_persist_behaviour.py` запускает оба
лаунчера со стабами `docker`/`nvidia-smi`/`curl`/`python3` и проверяет:
namespace следует реальным аргументам (fp8 и bfloat16 различаются), ошибка CLI
останавливает запуск с реальной причиной, override `KV_PERSIST_NAMESPACE`
соблюдается, обычный запуск ничего не выводит, `KV_PERSIST_BLOCK_SIZE` доходит
до движка, префикс model_name стабилен, а `auto` резолвится в dtype модели.
Тест поймал два реальных бага при разработке (необъявленная переменная `ROOT` в
пути вызова CLI и рассинхронизация префикса namespace).
