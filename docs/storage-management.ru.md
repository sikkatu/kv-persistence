# Хранилище и эвикция

## Модель бюджета

| Ограничение | По умолчанию | Кем обеспечивается |
|---|---|---|
| Жёсткий лимит | `KVP_CACHE_BUDGET_GB=1500` ГБ (1.5 ТБ) | `max_capacity_gb` L2-адаптера — записи сверх ОТКЛОНЯЮТСЯ |
| Физический потолок | свободное место на ОБЩЕМ диске ВМ (там же Docker-образы, веса модели, ОС). Preflight проверяет устройство через `KVP_CACHE_DEVICE` и сообщает свободное место. |
| Мягкий порог | 0.9 бюджета | `trigger_watermark` — здесь начинается автоматическая эвикция |
| Цель возврата | ~0.81 бюджета после одного цикла (0.9 порог х 0.9 от занятого) | `eviction_ratio` 0.1 занятой ёмкости |
| Квота пространства | опционально, `quotas.json` | слой политик `kvp-admin quota` |

Бюджет покрывает ТОЛЬКО постоянные KV-данные. Веса модели, ОС и прочие файлы здесь
не учитываются и ни один скрипт kv-persistence их не трогает.

Дефолт 1.5 ТБ — намеренно крупная доля ОБЩЕГО диска ВМ (там же лежат Docker-образы,
веса модели и ОС). Больше истории prefill на диске экономит время и энергию при
повторном открытии диалога, но оставьте запас для некэшевых записей — preflight
проверяет свободное место через `KVP_CACHE_DEVICE`. НЕ ставьте бюджет «сколько
осталось на диске»: оставьте >=50 ГБ под ОС/Docker/модельные нужды, и следите за
свободным местом по мере роста некэшевых писателей (docker pull, логи).

## Каким по длине может быть разговор?

Два разных лимита не путайте:

* **Лимит токенов одного разговора (~1M)** — ограничен контекстным окном модели
  (`max_position_embeddings` в `config.json` модели), НЕ этим кэшем.
* **Сколько истории кэш держит на диске** — ограничено только
  `KVP_CACHE_BUDGET_GB`. Токенных лимитов здесь нет: свыше 1 млн токенов имеет
  значение лишь граница переиспользования одного контекста (см. про переиспользование
  префикса в разделе «Архитектура»), а не kv-persistence как таковой.

Бюджет применяется ТОЛЬКО к данным постоянного KV-кэша. Веса модели, системные
и другие файлы никогда не учитываются и не трогаются этими скриптами.

## Учёт ёмкости

* Один файл на объект KV-чанка в `KVP_CACHE_ROOT` (временный файл + атомарный rename).
* Отдельного дискового индекса нет — детерминированное пространство имён файлов И
  есть индекс; при старте он восстанавливается лениво. `used_bytes` — сумма размеров
  реальных файлов кэша; отдельной строки «накладные расходы индекса» нет.
* Конкурентное добавление: приёмка сериализована внутри адаптера, а жёсткий лимит
  применяет сам адаптер LMCache `nixl_store_dynamic`
  (`max_capacity_gb`: записи сверх него отклоняются).
  `BudgetLedger.admit()` из этого репозитория даёт ту же проверку для вызывающего
  кода (см. `test_concurrent_admits_cannot_exceed_budget`), но на прод-пути записи
  **НЕ вызывается** (review round 13): LMCache пишет чанки, не обращаясь к нему.
  Поэтому квоты в `quotas.json` сегодня — это данные для ОТЧЁТОВ и ранжирования,
  а не точка принудительного ограничения записи: не считайте, что квота
  предотвращает рост хранилища, пока ledger не подключён к пути записи.
* **Учёт после ребута (NEEDS TESTING)**: после ребута `lmcache server` апстрим
  описывает ленивую перестройку индекса в памяти _по мере обращения к файлам_
  (только из их размера). Пока не подтверждено, что закреплённая сборка LMCache
  подает эти восстановленные размеры в `get_usage()` (и, следовательно, в учёт
  `max_capacity_gb` и LRU), нельзя считать, что прежние файлы остаются внутри
  жёсткого лимита. Обязательный аппаратный тест: заполнить кэш -> сделать
  рестарт -> продолжить запись -> проверить, что `used_bytes` продолжает расти
  в границах бюджета.

Отчёт в любой момент: `bash scripts/budget-report.sh status`

## Автоматическая эвикция (обязательна, всегда включена)

* Фоновый поток следит за `get_usage()`. Выше `trigger_watermark` политика
  вычищает до снижения ёмкости на `eviction_ratio`.
* Политика в работе — **LRU** по сохранённым ключам чанков (нативная для адаптера):
  именно она удаляет чанки в продакшене. `implementation/kvpersist/retention.py` —
  отдельный планировщик ценностного ранжирования (свежесть, переиспользование,
  длина префикса, байты), покрытый офлайн-тестами, но **НЕ интегрированный в
  производственный путь эвикции** — пока не рассчитывайте на него как на защиту
  ценных префиксов.
* Предупреждения давления: `soft_pressure: true` в отчёте; лаунчер предупреждает
  на старте при нехватке места на ФС.

### Явная очистка — только вручную
```bash
bash scripts/budget-report.sh purge --namespace=<model_name> --yes
bash scripts/budget-report.sh purge --all --yes
```
Пространства имён выглядят как `--models--MyModel--<hash>` (начинаются с дефиса),
поэтому передавайте значение как `--namespace=NAME` — форма `--namespace NAME`
(и позиционная) для имён с дефисом распознаётся argparse как неизвестные опции.
Позиционная форма работает для пространств без ведущего дефиса.
Требуется `--yes`. Удаление ограничено данными кэша внутри `KVP_CACHE_ROOT` —
всё остальное отклоняется с кодом 2. Пространство имён — это санитизированное
`model_name` (начальная часть имени файла L2 до хвоста
`_<rank8>_<group>_<hash64>.bin`), сопоставляется ТОЧНЫМ совпадением — посмотрите
имена пространств в `budget-report.sh status`. Если ничего не найдено, purge
завершается с кодом 1 и сообщением (никогда не молчит). Старт НИКОГДА не очищает кэш автоматически.
## Пространства и политика очистки

Адаптер L2 (`nixl_store_dynamic`) пишет ПЛОСКИЕ файлы с именами вида
`<safe_model_name>_<kv_rank:08x>_<object_group:x>_<chunkhash:64>.bin` прямо в
`KVP_CACHE_ROOT` — отдельных каталогов для пространств НЕТ. Поэтому пространство
имён — это префикс `model_name` этих файлов (начальная часть до хвоста
`_<rank8>_<group>_<hash64>.bin`), например
`--models--my_model--a84fadf1b808e8cfa5ef24f7a2924fa9`. Смена ревизии
создаёт НОВЫЕ пространства (новые префиксы файлов); старые НИКОГДА не удаляются автоматически
(задокументированная политика: очистка — явное решение администратора).
Для целенаправленного удаления посмотрите имена (`budget-report.sh status` →
`namespaces`) и выполните purge по имени (ТОЧНОЕ совпадение — без подстрок).
