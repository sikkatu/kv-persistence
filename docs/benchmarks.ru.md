# Бенчмарки

Правила замеров: каждое число обязано нести условия запроса (холодный/тёплый,
состояние процесса, состояние кэша). Ускорение БЕЗ доказательства дискового
восстановления НЕ закрывает первичную веху.

## Уровни доказательств тестов (что доказывает каждый уровень)

Три уровня строго разделены — никогда не путать одно с другим (review P1-2):

| Уровень | Тест / скрипт | Доказывает | НЕ доказывает |
|---|---|---|---|
| 1. File-level smoke | `tests/integration/test_l2_persistence.py::test_l2_file_survives_server_restart` | вручную записанные файлы переживают завершение процесса | что LMCache может перечитать собственные объекты |
| 2. Round-trip персистентности LMCache | `tests/integration/test_l2_persistence.py::test_lmcache_store_restart_retrieve_roundtrip` | LMCache пишет через реальный MP-протокол, первый сервер полностью останавливается, **новый** процесс на том же L2-каталоге извлекает объекты до рестарта, и контрольные суммы чанков совпадают | что vLLM + MiMo-V2.6-Pro переиспользует кэш в живом чате |
| 3. Полная приёмка vLLM | `scripts/test-recovery.sh`, `tests/recovery/` | реальная нагрузка vLLM переиспользует сохранённый KV после нужных рестартов (критерий приёмки проекта) | — |

### Уровень 2: round-trip персистентности LMCache (синтетический KV, без vLLM, без GPU)

Этот тест доказывает, что **сам LMCache** может восстановить данные из L2-яруса
после полного рестарта сервера. vLLM, модель и GPU не нужны.

* **Закреплённая версия / API**: LMCache **0.5.3** (пин в `requirements-lmcache.txt`).
  Тест управляет реальным MP-протоколом сервера через закреплённый CLI
  `lmcache bench server` (`--mode cpu --transfer-mode engine_driven`):
  `REGISTER_KV_CACHE_ENGINE_DRIVEN_CONTEXT`, `LOOKUP`,
  `QUERY_PREFETCH_STATUS`, `PREPARE_STORE`/`COMMIT_STORE`,
  `PREPARE_RETRIEVE`/`COMMIT_RETRIEVE` через ZMQ. Идентичность кэша строится
  на хэше токенов и детерминирована между запусками (`request_id` в
  `IPCCacheServerKey` исключён из равенства ключей), поэтому одни и те же
  идентификаторы нагрузки адресуют одни и те же объекты в более позднем
  запуске. Per-chunk MD5 байтов KV печатается как `CHECKSUM: <digest> (N chunks)`.
  Внимание: `--l2-adapter` принимает спецификацию адаптера как JSON-**строку**,
  а не путь к файлу (0.5.3 `add_l2_adapters_args`).
* **Зависимости**: Python 3.12, Linux с POSIX SHM (`/dev/shm`), закреплённый
  `lmcache==0.5.3` плюс `nixl==1.5.2` (L2-адаптер `nixl_store_dynamic` импортирует
  `nixl`), torch (достаточно CPU-сборки), pytest. GPU, CUDA и vLLM НЕ нужны.
* **Команда**:
  ```bash
  python3 -m venv ~/.venvs/lmcache
  ~/.venvs/lmcache/bin/pip install -r requirements-lmcache.txt
  export PATH="$HOME/.venvs/lmcache/bin:$PATH"
  KVP_LIVE_LMCACHE=1 python3 -m pytest tests/integration/test_l2_persistence.py \
      -k roundtrip -v
  ```
* **Что делает тест**: рендерит шаблон L2-адаптера репозитория в изолированный
  каталог `tmp_path` (продакшн-настройки сохранены: POSIX-бэкенд,
  `persist_enabled=true`), запускает реальный `lmcache server` на динамически
  выделенных портах, сохраняет детерминированную многочанковую синтетическую
  KV-нагрузку через реальный протокол, дожидается появления собственных
  data-файлов адаптера `*.bin`, полностью завершает процесс сервера, запускает
  **свежий** процесс на том же L2-каталоге и извлекает объекты до рестарта —
  с НУЛЕМ новых записей после рестарта. Контрольная сумма warm-прохода
  (вычисленная после очистки клиентских буферов в ноль и возврата данных
  через RETRIEVE) должна совпасть с ground-truth-суммой до рестарта.
* **Доказательство PASS**: `LOOKUP: N/N chunks hit` на свежем сервере,
  `RETRIEVE: retrieved`, ни одной строки `STORE: stored` после рестарта,
  совпадающие дайджесты `CHECKSUM` и негативный контроль (та же нагрузка,
  пустой L2-каталог) с `0/N` чанков — полный хит не может быть ложноположительным.
* **Разбор отказов**: stdout/stderr каждого сервера и каждый вывод bench
  дописываются в `<tmp_path>/roundtrip.log`; сообщения об ошибках называют
  упавший шаг (запуск / запись / остановка / новый запуск / промах кэша /
  извлечение / несовпадение checksum) и заканчиваются хвостом лога. Перезапуск
  с `-s` покажет итог PASS, а `pytest --basetmp=/some/dir` сохранит каталог.
* **Ограничение области**: нагрузка — синтетические KV-тензоры. Тест доказывает
  только уровень 2; сценарий vLLM + MiMo-V2.6-Pro + `MAX_NUM_SEQS=2` для чата
  Operit доказывается отдельно через `scripts/test-recovery.sh` (уровень 3).

### Уровень 2b: изоляция по идентичности на уровне API LMCache (без vLLM, без GPU)

Доказывает, что namespace идентичности kv-persistence разделяет
несовместимые конфигурации в РЕАЛЬНОМ хранилище LMCache — не только в локальных
метках.

* **Механизм (проверен по исходникам 0.5.3 и живым прогоном)**: ключ кэша LMCache
  (`ObjectKey.model_name`) также входит в имя файла L2 адаптера
  `nixl_store_dynamic` (`<safe_model_name>_<kv_rank>_<group>_<chunkhash>.bin`).
  Namespace встраивается в этот `model_name` через
  `CacheIdentity.lmcache_model_name()`, поэтому любое изменение идентичности
  переносит объекты на другой ключ И в другой файл на диске.
* **Команда**:
  ```bash
  KVP_LIVE_LMCACHE=1 python3 -m pytest \
      tests/integration/test_l2_persistence.py -k identity_namespace -v
  ```
* **Что доказывает**: одни и те же токены записаны под `model_name` идентичности A;
  поиск под A находит N/N чанков; для КАЖДОГО отдельно изменённого поля
  идентичности (model_id, model_revision, tokenizer_*, kv_cache_dtype,
  block_size, num_kv_heads, head_dim, tp_size, connector_version,
  max_model_len, chat_template_digest) изменённая идентичность получает `0/N`
  чанков на уровне API LMCache. Для `namespace_hint` проверяется, что он НЕ
  меняет ничего (это человеческая метка).
* **Известный пробел (измерен, не скрыт)**: `cache_salt` входит в равенство
  ключа, но НЕ входит в имя файла `nixl_store_dynamic` (адаптеры fs/s3/bigtable
  его учитывают). Поэтому вторичный (дисковый) поиск тех же токенов под ДРУГИМ
  соль-значением может после рестарта вернуть объекты исходной соли. Измерено
  живым прогоном: `store salt=tenantA`, `lookup salt=tenantB` -> возвращено
  `4/4` чанка. Тест `test_cache_salt_isolation_gap_in_nixl_store_dynamic`
  фиксирует это поведение и громко падает, если upstream это когда-либо
  исправит. **Не полагайтесь на `cache_salt` для изоляции на уровне L2**:
  пер-тенантный дискриминатор встраивайте в
  `lmcache_model_name(extra_discriminator=...)` или используйте отдельный
  корень L2-кэша на тенанта.

## Матрица (5 конфигураций × 3 масштаба промпта)

| # | Конфигурация | Что изолирует |
|---|---|---|
| 1 | Базовая: только in-memory prefix caching (прод-лаунчер) | эталонные TTFT/prefill |
| 2 | Персистентный кэш холодный (lmcache подключён, промпт впервые) | накладные расходы коннектора+хранилища |
| 3 | Персистентный кэш тёплый, тот же процесс vLLM | попадания в L1/L2 |
| 4 | vLLM перезапущен, кэш-сервис жив | восстановление из L2 → L1 |
| 5 | ОБА сервиса перезапущены, данные NVMe сохранены | полная персистентность (приёмочный критерий) |

Масштабы промптов: синтетические 32K / 128K / 256K токенов
(`scripts/benchmark.sh <сценарий> <токены>`), плюс реальные огромные истории
чата по доступности (`implementation/prompt_probe.py` сначала измеряет стабильный
префикс). Промпты 1M токенов исполняются только если железо допускает
осмысленное выполнение.

## Метрики на каждый прогон

`prompt_tokens`, `cached_tokens` (из `usage.prompt_tokens_details`),
`ttft_s`, `total_s`, байты кэша до/после (`budget-report.sh status`),
число строк LMCache (`Stored`/`Retrieved`), пики VRAM/RAM
(`nvidia-smi`, `/proc/meminfo` во время прогона), ошибки/фолбэки.

## Физические доказательства чтения с NVMe (не просто текст логов)

Разбор логов (слова `Retrieved`/`L2`) весьма версионно-зависим и был указан в ревью
как риск ложного PASS. Поэтому `test-recovery.sh` ДОПОЛНЯЕТ лог-доказательства
независимым физическим сигналом: счётчик секторов чтения закреплённого
NVMe-устройства (`KVP_CACHE_DEVICE`, читается из `/sys/block/<dev>/stat` поле 3),
измеряемый на протяжении каждого сценария. Сценарий, показывающий переиспользование
с НУЛЁВЫМИ физическими байтами чтения NVMe не может быть признан чтением из L2.

Если `KVP_CACHE_DEVICE` не задан или счётчик не читается — прогон
**INCONCLUSIVE** (exit 5): ни PASS, ни FAIL, поскольку недоказанный источник
диска никогда не должен считаться успехом.

## Таксономия исходов кэша

Успешная генерация ≠ успешное кашрирование. Каждый прогон классифицирует запрос
в РОВНО ОДИН исход:

| Исход | Требуются доказательства | Считается успехом? |
|---|---|---|
| **PERSIST-попадание** | события чтения из L2 после рестарта + `cached_tokens > 0` (если отчитывается) + нет перезаписи тех же данных | ДА — цель проекта |
| Попадание в памяти (L1/RAM) | `cached_tokens > 0`, но без доказательств L2 после рестарта | НЕТ (не доказательство персистентности) |
| Простое попадание в prefix cache | `cached_tokens > 0` без событий LMCache | НЕТ |
| Промах кэша (пересчёт) | нет переиспользования, свежий prefill | ожидаемо для холодных прогонов |
| Несовместимые данные | другое пространство, чистый промах | корректно, безопасно |
| Ошибка чтения/восстановления | строки ошибок адаптера/коннектора | НЕТ — жёсткий отказ |

## Критерий вердикта

PASS для первичной вехи требует ВСЕГО:
1. `cached_tokens > 0` на запросе после каждого рестарта (тесты 4 и 5);
2. LMCache-лог показывает события чтения из L2/диска после рестарта;
3. TTFT/prefill измеримо ниже сравнимой холодной базовой линии;
4. текст ответа остаётся корректным (ручная проверка);
5. байты кэша на общем диске ВМ не изменились через рестарты (доказывает данные ис-
   пользованы, а не перезаписаны).

Если в строке таблицы отсутствуют условия — повторите прогон перед выводами.
